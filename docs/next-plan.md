# pptx-nova 对比、检查与图片恢复编辑工作流增强方案

状态：待实现的设计方案。本文中的新增命令、参数、目录和报告 Schema 均为拟议接口，不表示已经发布。

更新日期：2026-11-15。

## 1. 建议与目标

为 `pptx-nova` 增加三个可独立触发的工作流，其中 Compare 和 Check 为只读分析，Image Restore 为以图片为来源的新 PPTX 创建：

1. **Compare：比较两个 PPTX，生成 HTML 差异报告。** 优先支持同一演示文稿的两个版本，结合语义差异与逐页视觉证据，回答“改了哪里、改了什么、哪些差异仍需确认”。
2. **Check：检查一个 PPTX，生成 HTML 或 Markdown 检查报告。** 整合结构、字体、链接、资源、兼容性和可选视觉检查，回答“发现了什么问题、问题在哪里、如何处理、哪些内容尚未检查”。
3. **Image Restore：将图片中的演示内容恢复为可编辑 PPTX。** 按区域恢复文字、形状、连接关系、表格及有可靠数据的图表，经过实际渲染校准与独立门禁验收；忠实恢复为默认模式，视觉增强在恢复基线上单独验证。

三个工作流复用报告展示、证据绑定及问题定位；Image Restore 另有对象识别、场景模型、确定性编译、版式拟合和 PPTX 发布门禁。Compare/Check 的报告完成状态不能代替恢复产物的验收结果。图片恢复的详细实施方案见第 14 节。

产品目标是把 `pptx-nova` 的使用场景扩展到已有文稿的审阅、验收与内容救援，形成“创建、接收或恢复文稿 → 检查 → 修改 → 对比验收”的连续流程。

### 1.1 用户价值

| 工作流        | 典型使用场景                                          | 主要收益                                     | 对产品吸引力的作用                            |
| ------------- | ----------------------------------------------------- | -------------------------------------------- | --------------------------------------------- |
| Compare       | 团队版本评审、翻译验收、翻新验收、外包交付核对        | 减少逐页查找变化的工作，清楚呈现变更与证据   | 报告效果直观，适合在案例和产品演示中展示      |
| Check         | 汇报前自检、客户来稿检查、其他工具生成文件的复核      | 将散落的检查结果变为可定位、可处理的问题清单 | 服务只想检查已有 PPT 的用户，增加独立使用入口 |
| Image Restore | 原始 PPT 丢失、只有页面截图、图表或流程图需要继续修改 | 恢复有实际用途的原生对象，并明确未恢复内容   | 提供直观的首次使用价值，服务存量材料救援需求  |
| 工作流组合    | 恢复后检查、修复，再对比修改结果                      | 验证对象能编辑、关键内容准确且修改符合预期   | 支持重复使用与后续任务衔接                    |

以上是基于使用场景和现有能力的产品判断，不能直接推导出新增用户量或付费转化率。发布后应通过真实任务完成情况和用户反馈验证。

### 1.2 成功标准

- 用户能通过自然语言进入三个工作流，无需了解底层 CLI 或 JSON 报告。
- 报告能离线打开，能够从摘要定位到具体页、对象或文件部件。
- 文字说明、预览图片和原始证据对应同一批输入与同一次运行。
- 没有发现问题、存在问题、检查不确定、检查未完成能够明确区分。
- 检查发现缺陷不会阻止交付问题报告；失败步骤及缺少的证据仍可见。
- 首版范围清晰，能力声明与实际运行时披露及证据一致。
- 图片恢复分别证明内容正确、目标对象可编辑、视觉达到约定标准及文件可用；未达标的候选不能标为成功恢复。
- 增强版本保留经过验收的忠实版本作为基线；改善不能牺牲关键内容、语义或要求的编辑性。

## 2. 当前基础与可复用能力

当前仓库已经具有比较和检查的基础能力，主要产物服务于 Agent 执行、验证及交付关卡。需要补充的是独立入口、综合报告模型和面向用户的展示。

图片恢复可以复用原生对象构建、回读和渲染能力，但识别、反演、拟合及图片参考验收需要新增独立层，不能通过增加一个报告模板就获得。

实现前必须重新探测实际 `xdoc`，读取对应命令和报告契约；本文不能替代运行时能力发现，也不要求刷新 `docs/xdoc-schema.json`。

### 2.1 当前语义比较的关键边界

按照已核对的 `pptx-diff/v1` 契约：

- 幻灯片按从 0 开始的索引匹配；用户报告统一显示从 1 开始的页码。
- 对象优先通过唯一对象 ID 与元素类型匹配，再尝试唯一对象名称与类型；歧义应保留为不确定。
- 正文、对象几何和样式具备明确的可靠比较范围。
- 媒体、图表数据和表格部分提供摘要级信息，不能据此承诺完整的二进制或逐单元格比较。
- 媒体二进制、表格单元格、SmartArt、动画等存在未支持区域；主题继承也有部分支持边界。
- `reliable` 可以作为已确认机器事实；`uncertain` 和 `unsupported` 需要单独展示。

因此，首版的核心定位是“同一演示文稿的版本比较”。任意两份独立创建的 PPTX 可以尝试比较，但报告必须解释页码对应和对象匹配的局限。

### 2.2 图片恢复的现有能力边界

- 可复用 `add-text-box`、`add-shape`、`add-connector`、`add-freeform`、`add-group`、`add-table`、`add-chart`、`add-equation` 和图片操作，以及 dry-run、apply、inspect 和渲染验证。
- 当前已核对的契约没有披露完整的截图 OCR、版面分割和图片到原生对象反演入口；这些属于拟新增能力。
- `visual-audit` 的参考输入为 PPTX；截图原图与候选渲染的比较需要新增适配与验收层。图片参考 PPTX 可以用于视觉展示，不能充当原生结构或数据真源。
- 自由路径按运行时支持的线段与三次曲线等契约构建，不假定任意 SVG 可以直接转换成原生形状。
- 可创建某种对象，不代表它在所有渲染器中保真；复杂图表、公式、效果和字体仍需逐项验证实际支持轴。
- 现有标准 Create runner 面向 DeckKit 内容合同，不能原样承接任意截图。Image Restore 需要独立的场景编译与门禁编排，同时保持现有创建、编辑关卡有效。

## 3. 产品入口与首版范围

### 3.1 自然语言入口

Compare 示例：

```text
比较 proposal-v1.pptx 和 proposal-v2.pptx，生成 HTML 差异报告。
重点列出文字、数字和布局的变化，不要修改原文件。
```

```text
比较翻新前后的两个 PPTX，生成逐页对比报告。
区分内容变化与样式变化，并标出无法确认的部分。
```

Check 示例：

```text
检查 proposal.pptx，生成 HTML 检查报告。
重点看字体、兼容性、文字裁切和重叠。
```

```text
检查 training.pptx，输出 Markdown 报告。
按严重程度列出问题、页码和修复建议。
```

以上 Compare/Check 请求进入只读分析工作流，不创建新演示文稿，不加载 DeckKit 创建流程，也不要求用户准备 `outline.json`、`deck_lock.json` 或编辑补丁。

Image Restore 示例：

```text
把 slide.png 恢复为可编辑 PPTX，尽量保持原图。
文字和流程节点必须可编辑，照片保持原样；列出无法可靠恢复的部分。
```

```text
将这张表格截图恢复成原生 PowerPoint 表格。
核对所有数字、单位和合并单元格，不确定的内容标出来。
```

```text
先忠实恢复这张截图，再提供排版更清晰的增强版。
不要改变文字、数字、连接关系和表达含义，附上原图与结果对照。
```

### 3.2 输出与分析档位

| 工作流  | 默认格式 | 其他格式                     | 默认分析档位                  |
| ------- | -------- | ---------------------------- | ----------------------------- |
| Compare | HTML     | 可选 Markdown 或两种同时输出 | `visual`：语义比较加视觉对照  |
| Check   | HTML     | Markdown 或两种同时输出      | `basic`：运行时支持的基础预检 |

分析档位与输出格式相互独立。Markdown 也可以引用视觉检查结果，HTML 的基础检查报告也可以没有预览图片。

- `basic`：收集所需的只读结构化证据，不要求渲染。
- `visual`：包含基础证据，并按工作流收集预览或规范视觉证据。
- 用户提到排版、重叠、裁切、视觉问题或要求页面截图时，Check 选择 `visual`。
- 用户明确指定的检查项目优先于默认集合；无障碍检查必须显式选入，不能描述成默认已完成。
- 用户要求的证据无法取得时，保留请求并报告未完成部分。可以交付已有结果，但不能将其包装成完整完成了原请求。

### 3.3 首版包含与后续扩展

| 优先级 | 内容                                                               |
| ------ | ------------------------------------------------------------------ |
| P0     | 两个只读入口、报告模型、HTML/MD 渲染、输入与证据绑定、部分失败报告 |
| P0     | 同源版本的语义比较、逐页视觉对照、可靠性分类及未配对页说明         |
| P0     | 基础预检、可选无障碍检查、可选视觉检查及问题定位                   |
| P1     | 跨页匹配提示、用户指定对应关系、既有翻译与翻新工作流自动附带报告   |
| P1     | 小型报告的单 HTML 文件模式、更多报告筛选与分享优化                 |
| P2     | 复杂重排与重建文稿的可靠语义匹配、依赖运行时增强的深层对象比较     |
| P2     | 明确规则支持下的修复后复检、问题状态追踪                           |

首版不承诺动画播放验收、PowerPoint 全功能兼容认证、完整无障碍合规认证、业务事实核验或全能设计评分。

### 3.4 Image Restore 的模式与范围

- 默认 `restore`：以原图为视觉依据，恢复用户要求的可编辑对象。
- 可选 `enhance`：先验收忠实恢复版本，再生成并单独验收增强版本。
- 默认输出是已通过恢复门禁的 PPTX 加恢复报告；请求范围未完成时，报告仍可交付，但候选不得冒充最终恢复文件。
- 首版重点验证清晰的页面截图、表格与二维示意图。模糊照片、遮挡、复杂背景、无法核实的数据和不可写对象进入明确的待核实或部分恢复状态。
- 图片重建不是只读报告，不套用 Compare/Check 的 `basic/visual` 完成定义；详细合同、状态和发布策略见第 14 节。

## 4. Compare 工作流设计

### 4.1 执行步骤

1. **建立运行与输入身份。** 确定 source/candidate 方向，创建新的运行目录，记录文件名、字节数与 SHA-256。同一内容的两份文件是合法比较输入。
2. **探测能力。** 保存本次运行的能力快照；按实际披露确认 inspect、diff 和所需渲染入口。
3. **检查对应关系。** 获取两份文稿的页数、尺寸及可披露的对象信息，声明首版使用索引对应；为页数不同、明显重排或对象匹配歧义生成对应关系提示。
4. **执行一次语义比较。** 对稳定输入运行 diff，保留摘要与同一次比较产生的完整证据；校验完整报告哈希、输入绑定和摘要一致性。
5. **收集视觉对照。** `visual` 档位冻结日期与渲染环境，复用现有比较编排、缓存和分页机制。需要逐页图片时，从同一批有效证据取得，或通过明确披露的 preview 路径补齐并记录来源。
6. **规范化变化。** 将正文、几何、样式、摘要级对象变化和不确定项映射到统一报告模型，保留原始类型与可靠性。
7. **生成解释。** Agent 可以概括变化及其可能影响，但解释必须关联具体变化 ID；主观判断与机器事实分开展示。
8. **发布报告。** 复核输入未变化，验证图片与证据引用，生成 HTML/可选 MD；未完成步骤和范围限制同时发布。

语义比较中没有发现已确认变化时，报告使用“在已覆盖范围内未发现已确认差异”。只有对应证据能够支持时，才说明文件字节相同、可比较对象相同或同一渲染器下像素相同，三者分别表达。

### 4.2 变化模型

普通差异是观察结果，不自动成为缺陷。

| 分类         | 典型内容                           | 展示原则                                         |
| ------------ | ---------------------------------- | ------------------------------------------------ |
| 文字变化     | 标题、正文、文本段落的增删改       | 显示前后文本；短文本可内联标记，长文本可展开     |
| 几何变化     | 对象位置、尺寸、旋转等已支持字段   | 以明确数值和对应页面为依据，避免猜测视觉影响     |
| 样式变化     | 字体、字号、颜色、边框等已支持字段 | 将可确认字段变化与主题继承的不确定性分开         |
| 摘要级变化   | 图表数据、表格或媒体摘要           | 标注比较粒度，保留证据能支持的结论               |
| 视觉变化     | 并排图片、运行时披露的变化区域     | 不将像素变化直接判为错误                         |
| 对应关系异常 | 页数不同、未配对页、对象身份歧义   | 提醒人工核对，不编造插入位置、移动关系或丢失对象 |
| 未覆盖区域   | 动画等当前不支持的区域             | 单独列出，不能计入“已检查且无变化”               |

文字中的数字变化可以突出显示，但普通数字字符串变化不能自动认定为图表数据错误或业务风险。

### 4.3 插页、重排与不同页数

- 首版原生语义结果仍按索引解释，不能在展示层偷偷重新编号后宣称完成了跨页语义匹配。
- 两侧超出配对范围的页面分别展示为未配对页，并保留各自预览和原始页码。
- 页数差异只能直接证明数量变化；中途插页、删除或移动的具体对应关系需要额外证据。
- 页标题、文本相似度和缩略图相似度可在后续版本提供“可能对应”提示；提示不升级为 `reliable`。
- 手动页映射可以先用于视觉浏览。用于语义比较前，需要有独立、可验证且绑定原始输入的匹配契约或运行时支持。
- 对比明显不相关的两份文件时，仍可交付观察报告，并明确其可比较范围和大量不确定项。

### 4.4 Compare HTML 内容

- 顶部：两份文件名称、比较方向、页数、分析范围、运行时间和完整性状态。
- 摘要：有已确认变化的配对页、变化类型数量、不确定项、未配对页与未覆盖区域。
- 导航：按原始页码浏览；可筛选“存在变化”“存在不确定项”“未配对页”。
- 逐页详情：左右预览、变化清单、前后文本、可确认字段、匹配方式及证据来源。
- 解释与限制：保留索引匹配边界、渲染环境差异和相关未覆盖项目。

第一版的 HTML 是差异审阅报告，承载预览与说明；PPTX 播放器、动画时间线和可编辑网页演示不在本期范围。

## 5. Check 工作流设计

### 5.1 执行步骤

1. **固定输入与范围。** 创建运行目录，记录输入身份、检查页范围、用户指定项目和目标 Office 版本。
2. **发现实际能力。** 保存能力快照，读取所需 action 的参数与报告契约。
3. **执行基础预检。** 按请求运行 `xdoc check`，默认采用实际披露的基础集合；单文件结构化结果使用其 `-o` 产物，不假设 stdout 是 JSON。
4. **执行明确选入的补充检查。** 例如无障碍检查，以及用户指定的字体或品牌规则；没有规则来源时不虚构品牌违规。
5. **收集视觉证据。** `visual` 档位按能力披露运行相关检查与规范渲染，保留 PNG、字体、布局和原生决策证据。
6. **整理问题。** 将问题归类、关联页面与对象、保留证据和检查状态，输出具体建议。
7. **生成报告。** 输出 HTML、MD 或两者，并保留所有未完成项目及原因。

`structure-check.mjs` 中部分逻辑依赖创建过程的预期字体、配色或设计锁，不能直接作为任意用户文稿的默认健康标准。应只复用能够脱离创建上下文、独立成立的检查；需要预期值的规则必须有用户提供的依据。

### 5.2 检查范围

| 类别         | 可以呈现的内容                                             | 必须保留的边界                                                     |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------ |
| 结构与兼容性 | 运行时披露的包完整性、解析及目标 Office 风险               | 完整包扫描不等于完整元素 Schema 验证，也不证明 Office 能无修复打开 |
| 字体         | 字体声明、嵌入情况、替代风险、实际渲染解析与字形问题       | 字体未嵌入、系统可用和最终字形缺失是不同结论                       |
| 链接         | 包内关系、链接清单及运行时明确报告的异常                   | 默认不联网探测 HTTP 状态，不能将链接存在描述为目标可访问           |
| 资源与策略   | 缺失或异常资源、已披露策略规则                             | 保留具体规则及范围，不扩大为通用安全认证                           |
| 视觉与布局   | 运行时确认的溢出、页面边界、布局或字体问题                 | 静态估算、实际渲染发现和 Agent 看图意见分别标识                    |
| 无障碍       | 标题、描述或装饰元数据、可静态判定的文字对比度等已支持规则 | 显式选择；不覆盖完整阅读顺序、屏幕阅读器行为或完整合规认证         |
| 用户规则     | 明确指定的字体、颜色、模板要求                             | 只有取得规则来源、可执行检查和对应证据后才给出结论                 |

Check 不应默认检查事实正确性、商业论证或数据真实性。用户另行提供事实来源时，可作为附加人工/Agent 审阅任务，单独记录方法与证据。

### 5.3 问题呈现与建议

每个问题至少包含：稳定问题 ID、类别、严重程度、证据类型、确定性、页码或包部件、对象定位（如有）、问题说明、建议及证据引用。

严重程度与确定性分别表达：高严重程度的疑似问题仍是疑似问题。普通变化不沿用问题严重程度。

建议采用 `high / medium / low / info`，映射规则与来源可追踪；保留底层原始等级，避免将各检查器的所有 warning 一律升级为严重缺陷。多个检查器描述同一现象时可以合并展示，但所有来源、影响范围及原始计数必须保留。

修复建议应具体到可执行的下一步，例如“核对第 5 页该文本框在目标字体下的实际换行”，并说明建议是否需要视觉复核。首版不自动修改 PPTX，不输出未经验证的自动修复承诺。

### 5.4 Check HTML / Markdown 内容

两种格式共享同一批结论和问题 ID：

1. 检查摘要：输入、范围、档位、运行状态、已确认与待复核问题数。
2. 优先处理清单：按严重程度及证据状态组织。
3. 详细问题：页面、对象、说明、证据及建议；HTML 提供关联预览。
4. 覆盖表：每项检查的执行状态、结论、检查页数和未完成原因。
5. 限制与环境：目标 Office、实际渲染器、字体环境及尚未取得的证据。

Markdown 采用相对资源路径；选择纯文本报告时，可以省略图片，但必须保留视觉结论的来源与限制。

## 6. 统一状态与报告数据模型

本节定义报告生成的公共状态；Image Restore 的恢复结果和 PPTX 发布结果使用第 14 节的专用状态，不能由报告成功推导。

### 6.1 区分四类状态

| 维度                     | 拟议状态                                                | 含义                                               |
| ------------------------ | ------------------------------------------------------- | -------------------------------------------------- |
| 运行完整性 `runStatus`   | `complete / partial / failed`                           | 请求的采集与报告步骤是否完成，不表示 PPTX 没有问题 |
| 检查执行 `execution`     | `completed / partial / skipped / unavailable / failed`  | 某个检查实际执行到什么程度                         |
| 检查结论 `assessment`    | `no-findings / findings / inconclusive / not-evaluated` | 仅针对该检查的有效范围给出结论                     |
| 事实确定性 `reliability` | `confirmed / uncertain / unsupported`                   | 结论有何种证据支持，与严重程度独立                 |

Compare 另有独立的变化结果 `changeStatus`：`confirmed-changes / no-confirmed-changes / inconclusive`。检查问题和版本变化分别存储，分别计数。

状态合并规则：

- 完成检查并发现问题，可以是 `runStatus=complete` 和 `assessment=findings`。
- 只有部分请求完成时，运行状态为 `partial`；已完成部分的发现仍然有效。
- 输入无法读取或无法形成有效分析时为 `failed`；输出位置可写时仍生成说明失败原因的最小报告。
- 用户明确选择 basic 后没有渲染，是该档位的正常范围；用户要求 visual 而渲染不可用，必须体现为未完成。
- 未检查、不支持和无法判定不能映射为通过，也不能计入无问题页数。
- 有未覆盖内容时，“未发现问题”必须附带对应范围，不能成为整个 PPTX 的质量保证。

### 6.2 拟议报告模型

新增 skill 自有 Schema：`pptx-nova-review-report/v1`。这是报告聚合模型，不替换或改写任何 `xdoc` 原生报告。图片恢复复用展示与证据字段，通过专用扩展记录恢复范围、对象映射和门禁；其场景与发布合同见第 14 节。

| 字段                                | 内容                                                             |
| ----------------------------------- | ---------------------------------------------------------------- |
| `schemaVersion`、`kind`、`reportId` | 模型版本、`compare/check/image-restore` 类型及报告身份           |
| `request`                           | 输出格式、语言、档位、请求范围、检查集合、目标 Office            |
| `inputs`                            | 输入角色、显示名称、字节数、SHA-256；内部证据另存真实路径        |
| `runtime`、`renderContext`          | 实际运行时版本、能力快照摘要、实际渲染后端和冻结日期等已取得信息 |
| `runStatus`、`summary`              | 执行完整性、变化计数、问题计数及范围摘要                         |
| `checks[]`                          | 每个检查的执行状态、结论、原始报告版本、覆盖与原因               |
| `slidePairs[]`                      | Compare 的左右原始页号、匹配方式、可靠性、预览与变化引用         |
| `changes[]`                         | 已确认或不确定变化、类型、前后值、位置与证据                     |
| `issues[]`                          | 检查问题、严重程度、确定性、位置、建议与证据                     |
| `coverage`、`limitations[]`         | 请求范围与实际范围、未配对页、未检查及未支持项目                 |
| `evidence[]`、`artifacts[]`         | 证据身份、报告内资源位置、字节数、哈希及来源引用                 |
| `review`                            | 实际 Agent/人工审阅的存在性、范围与绑定；没有审阅时如实记录      |

数据约束：

- 原生页码、对象 ID、部件名和可靠性保留；展示转换与原始值分别保存。
- 对象不存在或未披露时使用明确的空定位，不通过文本搜索猜出一个对象 ID。
- 原始报告版本和 JSON Pointer 等定位信息可用于追溯；未知字段保留在原始证据中，不为适配而删改证据。
- Agent 解释使用单独字段，引用变化或问题 ID；不能覆盖机器值、原生决策或输入身份。
- 去重后的展示计数、原始发现计数和实际检查覆盖分别统计。
- HTML 与 MD 只读取这一模型，禁止分别计算统计或生成互相矛盾的结论。

## 7. 报告交付、离线浏览与资源管理

### 7.1 默认交付目录

首版优先采用目录式离线报告，避免长文稿将图片全部内嵌后造成 HTML 体积失控。

```text
proposal-review/
├── report.html
├── report.md              # 请求 Markdown 时生成
├── report.json            # 规范化报告数据
├── manifest.json          # 本次交付资源清单与哈希
└── assets/
    ├── source-slide-001.png
    ├── candidate-slide-001.png
    └── ...                # 按工作流与实际证据生成
```

运行目录保留原始证据：

```text
.pptx-nova/<slug>-<timestamp>/
├── xdoc-capabilities.json
├── render-context.json            # 发生渲染时
├── request.json
├── evidence/                      # 原始报告、命令结果与日志
├── previews/                      # 实际生成的预览或比较图片
├── normalized-report.json
└── publication-manifest.json
```

以上文件只在实际生成时出现；不能为了凑齐目录而制造成功证据。交付资源必须复制或可靠物化到交付目录，不能依赖运行目录中随后可被清理的文件。

### 7.2 HTML 行为

- 通过 `file://` 直接打开，不要求本地 HTTP 服务。
- CSS、交互脚本和所需数据随报告提供；浏览器不通过 `fetch()` 读取本地 JSON。
- 默认使用本地字体栈，不加载 CDN、外部字体、遥测或第三方脚本。
- 支持文字搜索、类别筛选、仅显示有变化/问题的页面、详情展开和图片放大。
- 预览采用缩略图导航与按需加载，避免首屏解码整份大文稿。
- 使用文本标签表达状态，兼顾键盘操作、可见焦点、可读对比度和图片说明。
- 报告语言随用户请求选择；机器字段、规则 ID 和状态码保持稳定。

对 PPTX 文本、文件名和诊断信息进行正确转义；内嵌数据采用安全序列化，防止 `</script>` 等内容成为活动代码。HTML 不执行源文稿里的指令，也不自动访问其中的链接或本机路径。

### 7.3 分享与证据可追溯性

- 用户可见报告默认使用显示名称与相对资源路径，不泄露本机绝对路径。
- 原始输入 PPTX 和完整备注不自动打包进报告；展示范围由任务需求确定。
- 报告可记录原始证据版本、哈希及定位信息；未打包的原始证据不生成失效下载链接。
- 原始证据默认留在运行目录，需要附带时再作为明确的交付内容处理。
- 分享时需要携带整个报告目录。后续单文件模式设置明确的体积预算，超出后提示使用目录模式，不能静默删图或删发现。

## 8. 技术架构与拟议接口

### 8.1 职责划分

```text
用户请求与 Skill 路由
        ↓
Compare / Check 编排入口
        ↓
运行时能力发现 + 只读证据采集
        ↓
原始证据校验 + 规范化报告模型
        ↓
HTML / Markdown 渲染
        ↓
资源完整性校验 + 报告发布
```

采集层负责调用现有 CLI 并保留退出码、stdout、stderr 和文件产物；适配层负责解释原生状态与覆盖；展示层不重新运行检查或改变结论。

### 8.2 拟议文件布局

```text
pptx-nova/
├── scripts/cli/review/
│   ├── compare-report.mjs
│   └── check-report.mjs
├── scripts/lib/reports/
│   ├── collect.mjs
│   ├── normalize.mjs
│   ├── model.mjs
│   ├── render-html.mjs
│   ├── render-markdown.mjs
│   └── publish.mjs
└── references/review/
    ├── compare-report.md
    └── check-report.md
```

文件名为建议；实施时按实际职责合并，避免只有转发用途的空模块。报告 Schema 保持在 skill 内，可先由 `model.mjs` 导出；需要独立 JSON 文件时，与现有资产目录约定对齐。

工程约束：

- 发布脚本全部使用 Node.js 20+ 可直接运行的 `.mjs`，仅使用 Node 内置模块和已发布 `xdoc`。
- 不增加 Python、Nushell、浏览器自动化或第三方 npm 包作为用户运行依赖。
- skill 内部模块不 import CLI 入口；需要调用现有命令时通过进程参数数组执行，路径由 `skill-paths.mjs` 解析。
- 现有 `compare.mjs` 的 PNG/JSON 行为和调用方保持兼容；新 HTML 入口使用独立命令。
- 不修改 DeckKit、共享几何核心或创建/编辑交付策略来实现报告功能。

### 8.3 拟议 CLI

以下为新 skill 脚本的设计示例，不是已有 `xdoc` 参数：

```bash
node <skill-root>/scripts/cli/review/compare-report.mjs \
  --source before.pptx --candidate after.pptx \
  --profile visual --format html \
  --output-dir ./comparison-report --locale zh-CN

node <skill-root>/scripts/cli/review/check-report.mjs \
  --input proposal.pptx --profile basic \
  --format html,md --target-office 365 \
  --output-dir ./inspection-report --locale zh-CN
```

通用参数应覆盖输入、输出目录、格式、档位、语言、明确页范围、可选运行目录和 `xdoc` 路径。Check 提供检查集合与目标 Office；Compare 首版只提供契约允许的索引范围，不伪装成已有跨页映射接口。

默认禁止覆盖已有交付目录；输入与输出不得互相别名。中间证据在当前运行内生成，完成后以临时目录校验并发布，避免留下看似完成却缺图的最终报告。

### 8.4 报告执行状态与退出码

新脚本拥有独立的退出约定，不能直接套用某个底层命令的数值：

| 拟议退出码 | 含义                                                |
| ---------- | --------------------------------------------------- |
| `0`        | 所选范围的报告完整生成；PPTX 可以仍有问题或需要复核 |
| `2`        | 参数无效，尚未启动有效分析                          |
| `3`        | 已交付部分报告，存在请求步骤或范围未完成            |
| `4`        | 无法完成有效分析；可写时交付失败说明报告            |
| `5`        | 报告自身生成、资源验证或发布失败，不能声称交付成功  |

这些是新报告包装器的拟议状态，不是 `xdoc` 退出码。底层退出码、原始错误类型与报告始终保留。需要自动化“发现高严重程度问题即失败”的策略可后续添加显式选项；默认不将问题数量和报告交付失败混为一谈。

## 9. 证据、运行环境与现有关卡的关系

### 9.1 证据要求

- 每次新任务建立独立运行目录并重新探测能力。
- 在采集前后检查输入哈希；输入在运行中变化时，标记证据失效，使用新运行重新分析。
- 语义 diff 的摘要与完整证据来自同一次比较，并按现有 helper 校验。
- 渲染记录冻结的动态字段日期、实际运行时和可取得的渲染器信息；两侧环境一致。
- 图片、PDF、清单和报告建立哈希绑定；缓存键遵循输入、实际 PDF 与渲染上下文约定。
- 单独记录预览、规范视觉证据、静态估算、Agent 看图审阅及人工审阅，不能相互替代。
- 不填造未披露能力、未执行检查、缺少的对象定位或不存在的截图。

### 9.2 报告发布与 PPTX 交付分别处理

检查报告描述现状，发现问题后应继续生成报告。`visual-audit` 原生 `stop` 或 `require-human-confirmation` 等结论原样保留，在报告中解释；它们不是阻止输出问题报告的理由。

同时，成功生成报告不能授权交付或修改一个未通过关卡的 PPTX：

- 报告模型不新增或伪造 `deliveryAuthorized=true`。
- 现有 Create、Edit、Translation、Refurbish 的规范视觉及语义关卡继续生效。
- 后续“根据报告修复”的请求进入原有编辑流程，独立绑定输入和修改范围。
- 实际 PowerPoint 播放、独立渲染器或人工审阅证据缺失时，如实标为未取得。

### 9.3 环境问题处理

渲染依赖、字体、资源、配额或许可导致某步不可执行时，只在该检查和完整性摘要中说明实际原因与下一步；保留已完成结果。不能自动放宽用户约束，也不能通过换格式、拆任务等方式绕过限制。

用户文档中的相关说明继续集中在既有简短章节及详细指南，新工作流的安装与首次使用说明不重复展开许可条款。

## 10. 性能与长文稿处理

- 基础检查与视觉检查分档，避免纯结构任务承担不必要的渲染成本。
- 复用现有比较的分段、并发及缓存机制；两侧相同输入按有效缓存约定复用。
- 一次稳定输入只执行一次完整语义比较；报告筛选和格式转换不重复采集。
- 大型比较按页面或分段组织资源，不生成一张无法浏览的超长总图作为唯一证据。
- 有效证据优先复用；确需不同预览时记录其来源，不将其冒充规范视觉证据。
- 记录页数、检查项目、各步骤耗时、渲染次数、缓存命中及产物字节数。
- 性能目标在明确硬件、字体、运行时、文稿规模和档位下建立基线，发布前不承诺未经测量的固定秒数。

## 11. 实施阶段与交付物

### 阶段 A：报告基础层

交付：模型、状态语义、HTML/MD 渲染、资源清单、离线浏览及安全序列化。

完成条件：同一规范化输入能够生成结论一致的两种格式；部分结果、长文本、恶意文本和缺少可选证据能够正确呈现。

### 阶段 B：Check 基础入口

交付：能力发现、基础预检适配、显式无障碍选项、问题归类、修复建议字段和基础报告发布。

完成条件：可检查用户已有 PPTX；发现问题仍交付报告；无依据的字体、品牌或质量规则不会生成违规结论。

### 阶段 C：Compare 入口

交付：索引匹配声明、语义差异适配、完整证据绑定、视觉对照、未配对页和 HTML 导航。

完成条件：同源版本变化可定位；无变化和不确定结果准确区分；插页、重排、对象重建不会被描述成可靠跨页匹配。

### 阶段 D：视觉检查与发布完善

交付：Check visual 档位、规范视觉证据适配、真实看图审阅标记、长文稿与失败恢复体验，以及两个入口的完整文档。

完成条件：原生决策被保留，未检查项目可见，截图与输入一致，既有创建/编辑工作流无回归。A 至 D 构成 Compare/Check 首版，可在 B/C 阶段分别开展限范围试用。

### 阶段 E 至 H：Image Restore

图片恢复按独立质量目标交付：E 建立输入与场景合同，F 完成清晰文字和基础图形恢复，G 增加表格、图表与编辑验收，H 完成增强模式和发布验证。每阶段的详细产物、依赖与通过标准见第 14.13 节。

### 后续迭代

依据试用问题优先处理页面匹配、单文件分享、报告自动附带及修复后复检。高级匹配与深层对象比较的范围，应先确认新增运行时契约或独立匹配方法，不能只调整展示文案。

## 12. 验证矩阵与验收标准

### 12.1 必须覆盖的场景

| 类别    | 场景                                   | 预期结果                                                     |
| ------- | -------------------------------------- | ------------------------------------------------------------ |
| Compare | 相同文件、同字节副本                   | 准确表达字节相同；未执行的其他验证仍有明确状态               |
| Compare | 单页文字、数字、位置或字体变化         | 在支持范围内定位已确认变化，前后值与原始证据一致             |
| Compare | 开头或中间插页、删页、重排             | 解释索引限制，显示未配对或疑似对应，不将页移动当成已确认事实 |
| Compare | 重复对象名、ID 变化、重新创建对象      | 保留不确定匹配，不制造精确对象对应                           |
| Compare | 表格、图表、SmartArt、动画             | 呈现实际比较粒度和未覆盖区域                                 |
| Check   | 字体、包关系、资源或兼容性风险         | 保留规则、范围、严重程度与具体证据                           |
| Check   | 静态估计与渲染证据不同                 | 分别呈现来源，不根据单个信号伪造统一通过结论                 |
| Check   | 无障碍未选择、已选择但无法判定         | 分别显示未检查或不确定，不能默认为通过                       |
| 通用    | 选页检查、全部检查、两侧页数不同       | 请求范围与实际覆盖准确，范围外不计入通过                     |
| 通用    | 渲染不可用、转换被拒、子命令失败       | 保留已有结果，生成部分报告和明确失败步骤                     |
| 通用    | 输入缺失、损坏或运行中变化             | 输出明确分析失败或证据失效状态，不发布旧结果冒充新结果       |
| 通用    | 原始证据被替换、图片缺失、哈希不符     | 拒绝成功发布或标记报告损坏，不能展示为完整可信报告           |
| 展示    | 中英混排、超长文本、大量问题与长文稿   | 内容完整、导航可用、无静默截断                               |
| 展示    | HTML/脚本片段、特殊文件名及外部链接    | 作为数据显示，不执行、不自动访问                             |
| 交付    | 离线打开、移动报告目录、输出目录已存在 | 资源可解析；现有用户内容不被覆盖                             |

> 比较两个 PowerPoint 版本并生成 HTML 差异报告；检查已有演示文稿并输出 HTML 或 Markdown 问题报告；将图片中的文字、图形与可核实数据恢复为可编辑 PPTX，附上恢复范围及原图对照。

展示案例优先选择少量明确变化的同源版本，以及带可验证问题的检查样例。示例应同时展示报告摘要、页面定位和可信证据，不宣传“所有差异均可识别”或“通过检查即可保证完美播放”。

图片恢复案例同时展示实际编辑操作、原图与结果局部放大、数据来源及未恢复区域，避免仅用整页视觉相似度宣传完全恢复。

试用期记录或由用户主动反馈以下信息，不默认增加遥测：

- 报告是否成功完成，部分失败最常发生在哪一步。
- 用户是否能够找到具体问题或变化，并据此继续处理。
- 不确定匹配和疑似问题的复核结果。
- 是否出现重复使用、报告分享或“根据报告修复”的后续请求。
- 不同文稿规模与分析档位的耗时、体积和可读性。
- 图片恢复中可核实内容的正确率、要求的原生对象完成率、待核实区域及实际编辑成功情况。

根据这些证据决定下一阶段投入，优先改善报告可信度、定位效率和实际任务完成率。

## 14. Image Restore：图片恢复编辑详细实施方案

### 14.1 产品合同与质量目标

采用“区域语义恢复 → 确定性原生对象构建 → 实际渲染校准 → 独立验收”的路线。默认忠实恢复，增强版本在已验收的忠实版本之上另行生成。原图、用户补充数据和已验证候选分别保留。

“不能更差”落实为明确的非退化条件：

1. 原图可确认的文字、数字、单位、公式及连接关系不被错误替换或遗漏。
2. 用户要求恢复的对象具有相应原生语义，并通过实际编辑验收。
3. 关键区域达到事先定义并经样本校准的视觉容差，没有新增可见缺陷。
4. 增强不损害内容、数据关系、要求的编辑性及受到保护的视觉属性。
5. 任一必要条件无法证明时，保留候选和诊断，不能宣称完整恢复成功。

截图不包含底层图表数据、原始字体身份、被遮挡内容或对象树。对任意低质量输入不能承诺自动恢复全部信息，也不能将模型的主观“更好看”作为非退化证明。承诺必须绑定实际输入、请求范围、目标环境和已完成的验收项目。

### 14.2 输入评估与源文件优先级

首版图片入口以实际运行时支持的 PNG/JPEG 为目标，可恢复整页或明确选定的区域；多图按用户顺序对应多页。其他格式通过能力发现决定，不静默忽略不支持的文件。

执行前评估：

- 图片有效性、解码后尺寸、页面比例、方向、文字像素高度和压缩噪声。
- 是否含浏览器边框、拍照透视、裁切、遮挡、模糊、旋转或复杂背景。
- 是否存在多页拼图，是否能确定各页边界及顺序。
- 用户目标是整页可编辑、某些对象可编辑，还是单张表格、图表或示意图恢复。
- 用户是否提供字体、原始图片、图表数据、公式文本等补充材料。

原始图片保持只读并记录哈希。裁边、旋转或透视纠正生成独立的规范化参考，保留变换及逆映射；不能裁掉内容、虚构遮挡区域或把增强后的图片当成原始证据。

如果用户同时提供原始 PPTX，优先走原生提取或编辑。PDF 可以提供页面图及已披露的文字信息作为辅助，但不据此承诺已经恢复 PDF 的逻辑对象或原始 PowerPoint 数据。

画布先保持图片有效区域的宽高比，按明确比例映射到 PPTX 单位。截图像素和显示 DPI 不能直接证明原始幻灯片尺寸或字号；尺寸选择和坐标变换写入合同。

### 14.3 整体执行架构

```text
输入图片 + 用户恢复目标 + 补充材料
                  ↓
输入身份与质量评估、规范化参考
                  ↓
文字识别 + 区域分割 + 结构/关系识别
                  ↓
内容核实与恢复合同 + 带证据的场景模型
                  ↓
区域表示选择 + 几何/字体约束拟合
                  ↓
确定性编译 xdoc patch → dry-run → apply
                  ↓
inspect 回读 + 规范候选渲染
                  ↓
内容 / 编辑性 / 局部视觉 / 文件质量门禁
                  ↓
未达标：定位问题 → 局部修正 → 重新检查受影响范围
达标：发布忠实版本 → 可选增强与重新验收
                  ↓
PPTX + 原图对照 + 恢复范围与限制报告
```

Agent 负责语义解释、识别候选与真实图片审阅；编译器和校准器负责有边界的数值、几何及样式处理。模型不直接承担无约束的整页坐标、对象结构和补丁格式生成。

### 14.4 恢复合同与场景模型

拟议新增 `pptx-nova-restoration-contract/v1` 和 `pptx-nova-restoration-scene/v1`，均为 skill 自有模型，不伪装成 `xdoc` 已发布报告。

| 模型内容 | 必须记录的信息                                               |
| -------- | ------------------------------------------------------------ |
| 输入身份 | 原图、规范化图、补充材料的哈希及来源                         |
| 恢复目标 | 全内容恢复或指定目标，哪些对象必须可编辑，哪些资源按图像保留 |
| 坐标合同 | 源像素画布、有效区域、PPTX 画布、变换与单位                  |
| 内容锁   | 文字、数字、单位、公式、数据与关系的来源和核实状态           |
| 场景对象 | 稳定逻辑 ID、类型、边界、层级、分组、角色与候选表示          |
| 文字结构 | 行和段落、富文本、基线、候选字体、字号、边距及断行约束       |
| 关系结构 | 连接方向、端点、节点归属、表格网格与合并、图表系列和数据来源 |
| 视觉约束 | 对齐、间距、层叠、比例、颜色语义和不得改变的关键区域         |
| 不确定性 | 逐字段的观察、推断、来源、待核实项及已知限制                 |
| 编译绑定 | 逻辑对象到实际 slide/shape/group 的映射和候选哈希            |
| 验收策略 | 策略版本、关键区域、视觉容差、编辑测试和实际目标环境         |

同一个对象的文字、字体与几何可以有不同确定性，不用一个整体置信分数覆盖全部字段。未核实内容可以参与草稿预览，但不能越过必要的内容门禁。

用户明确要求整页可编辑时，合同覆盖所有可见语义内容；不能把困难对象排除出目标后重新计算成完成。只有用户本来就指定局部恢复时，才按该范围验收。

### 14.5 识别、分割与内容核实

先识别文字与图形区域，再恢复区域内部结构和区域间关系：

1. 获取文字行、词或字的定位信息，识别段落、语言、富文本差异与阅读顺序。
2. 分离照片、背景、文字、节点、连接线、表格、图表和复杂复合区域。
3. 推断重复网格、共同对齐、分组和遮挡顺序；所有推断保留证据与状态。
4. 对数字、小数点、负号、百分号、单位、脚注及公式符号做专项核对。
5. 对关键歧义进行局部放大、不同识别路径比对或人工/用户核实；仍无法确定则保留待核实状态。

识别器自报置信度只用于排序与复核调度。两个模型给出相同结果也不自动证明正确；内容验收必须能回到源区域或用户提供的可靠资料。

图表的几何高度只能支持近似读数；没有精确标签或用户数据时，不把推测值写入原生图表后宣称恢复了真实数据。表格空白、不可见单元格和遮挡文字也不得根据上下文补写为事实。

源图中的文字及识别结果均为任务数据，不执行其中的命令、访问指示或工作流要求。识别输出需通过 Schema、范围及资源约束校验后进入编译。

### 14.6 按区域选择恢复表示

| 内容类型                 | 优先表示                             | 需要验证的条件                          | 无法满足时                             |
| ------------------------ | ------------------------------------ | --------------------------------------- | -------------------------------------- |
| 标题、正文、标签         | 原生文本框与富文本                   | 文字正确、断行合理、实际字体可用        | 标记待核实，不转轮廓冒充文字编辑       |
| 简单形状与卡片           | 原生预设形状                         | 几何、填充、轮廓、圆角及可见性          | 尝试受支持自由路径，或说明未恢复       |
| 流程图与组织架构         | 原生节点、连接线和合理分组           | 连接方向、端点、路由及移动后的维护性    | 对歧义边进行核实，不能随意猜连线       |
| 自定义二维图形           | 有界的原生自由路径                   | 在已支持线段/曲线子集内，轮廓与拓扑正确 | 保留图像并标明编辑限制                 |
| 表格                     | 原生表格                             | 单元格内容、合并、行列结构和内部排版    | 不能用矩形加文本集合宣称原生表格恢复   |
| 数据已核实图表           | 原生图表                             | 类型、系列、数据、轴及标签含义正确      | 调整表示前说明不能满足的保真或语义条件 |
| 数据未核实图表           | 原始图像与待核实记录                 | 清楚标记数据编辑未完成                  | 所需数据取得前不能通过全内容恢复门禁   |
| 数学公式                 | 已支持的原生公式或用户允许的资源表示 | 表达式与实际编辑方式正确                | 明确 SVG/图片不等于原生公式编辑        |
| 照片、产品截图、复杂插画 | 保留源图像资源                       | 裁剪、比例、清晰度和资源归属正确        | 请求更合适的源资源或保留明确限制       |

图片保留是角色相关的选择：照片通常以图片对象实现移动、缩放和替换；含有应恢复文字、数据或节点的复合截图不能同样计入语义编辑完成率。

背景处理是硬条件：

- 原图中的文字被恢复后，不能在其下保留同一段栅格文字。
- 纯色或可可靠重建的背景按对象重建，恢复文字区域不依赖遮盖旧字。
- 文字覆盖复杂照片时，优先使用用户提供的干净背景资源；原图无法提供的背景信息不能被认定为已经还原。
- 生成式补背景仅能作为明确记录的推测性候选，不得成为忠实恢复的默认真源。必要条件无法验证时，该区域保持未恢复状态。
- 用实际改字、移走文本框和检查底层区域的测试发现重影、旧字与遮盖残留。

SVG 插图、文字轮廓或大量碎片路径可以提供视觉结果，但不能据此宣称恢复了文字、表格或图表的语义编辑能力。

### 14.7 确定性编译与原生构建

编译器只消费通过合同验证的场景模型，输出当前运行时支持的类型化操作：

- 通过坐标变换统一像素、页面单位和自由路径局部坐标，处理舍入与画布边界。
- 为语义对象生成稳定名称、逻辑映射及分组；实际对象 ID 由回读结果确认。
- 使用明确的文本边距、字体及样式，保留有意义的行和段落，不通过逐字拆框伪造普通段落。
- 自由路径只编译已支持的命令；连接点按具体预设与当前契约选择，不能采用统一方位编号猜测端点。
- 表格同时设置网格、行高、内边距和字体；图表以已核实数据及受支持类型构建。
- 资源路径通过 skill 内的运行时路径工具处理，图像资产绑定输入及实际区域。

随后执行完整 patch 校验、dry-run、apply 和 inspect，核对对象类型、文本、表格数据、图表数据、连接及资源。回读与场景一致只证明写入正确，不能替代原图内容识别的正确性验证。

忠实恢复以原图布局为约束，不强制套用某个 DeckKit。需要独立的创建路由、场景合同及验收消费者；不能把未经过合同的新 patch 塞入现有 runner 的无关参数。通用渲染与证据模块可以复用，现有发布关卡不得通过改名、伪造模式或伪造参考源绕过。

### 14.8 渲染校准与有界优化

以同一候选的实际 xdoc 渲染作为拟合对象，原图或已记录变换的规范化图作为外部视觉依据。

按三轮组织：

1. **整体结构轮**：画布、主要区域、层叠、对象比例、分组与关系。
2. **文字和几何轮**：字体候选、字号、基线、换行、文本框、节点与连接线位置。
3. **局部细节轮**：线宽、颜色、圆角、边距、效果和图表标签。

OCR 的字形边界不是 PowerPoint 文本框。拟合应考虑真实字体测量、字形墨迹、文本框内边距和基线，使用实际排版结果校准。字号、字距和行距有可读性约束，不能仅靠缩小文字消除溢出。

优化器采用有限候选和明确参数边界，记录每轮目标、改变项、证据及结果。关键内容与目标编辑性为硬约束；局部视觉改善不能抵消内容错误。已验收区域锁定，涉及依赖时重新检查邻近区域或整页。

每轮保留候选与最佳已验证状态；退化时回退。设置最大轮数、时间或无改善停止条件，避免无限“看图再重画”。更换识别模型、字体、运行时或源图后，重新确认相关绑定和验收结果。

原截图的渲染器及字体环境通常未知，报告应准确记录候选环境，不能把它称为与原稿同渲染器等价。图片对照需要容纳已校准的抗锯齿与采样差异，但不得通过非刚性变形、模糊或扩大容差掩盖对象错位、文字错误及缺失。

### 14.9 多维验收与编辑操作测试

恢复验收独立检查以下维度，不用一个全页相似度分数代替：

| 门禁         | 验证内容                                              | 典型阻断条件                                     |
| ------------ | ----------------------------------------------------- | ------------------------------------------------ |
| 内容正确性   | 已核实文字、数字、单位、公式、表格/图表数据及连接关系 | 关键内容错误、遗漏、未解决歧义或无来源数据       |
| 目标编辑性   | 要求恢复的语义对象类型、实际编辑能力和未恢复区域      | 用图片、文字轮廓或碎片路径代替要求的语义对象     |
| 视觉保真     | 整页及关键区域的布局、文字、轮廓、颜色与显著细节      | 关键区域超出校准容差，出现错位、缺失、重影       |
| 页面质量     | 实际文字适配、遮挡、边界、字形与图形可见性            | 新增裁切、溢出、缺字、不可读文字或不可见证明对象 |
| 文件与兼容性 | 结构、资源、回读和用户要求的目标环境验证              | 文件损坏、关键资源缺失或必要目标验证未完成       |
| 实际审阅     | 最终候选的真实 PNG 与必要目标应用证据                 | 审阅范围不全、证据陈旧或关键问题未处理           |

视觉比较结合整页概览、关键区域局部放大、文字位置、边缘/结构差异和颜色差异。原图与候选使用记录过的坐标与采样策略；关键数字、标签和连接端点不能被大面积相同背景淹没。

阈值以固定版本的验收策略维护，在具有已知正确内容的样本、负例和未参与调参的样本上校准。不得直接把某个 SSIM 或全图像素阈值宣传成高保真保证。只要关键内容门禁失败，视觉指标再高也不能通过。

编辑性验收在独立测试副本中执行，测试后的文件不替代最终候选：

1. 修改原生标题或标签，检查旧字是否残留；适度增加长度，核对文本框具备合理编辑能力。
2. 修改表格单元格，回读内容与合并关系，检查相邻单元格和布局。
3. 修改图表数据，确认原生数据与显示同步，原始恢复的数据来源仍可追溯。
4. 移动流程节点，核对其连接关系及已承诺的连接维护行为。
5. 调整或替换图片，确认图像资源独立，相关文字不被错误烘焙在同一资源中。

每个强制恢复目标必须有类型验证和相应编辑测试。可对重复对象记录复用的测试依据，但不能只抽查标题后宣称所有表格、数据或连接均可编辑。任意长度文本的自动适配不在默认保证内，编辑测试的条件和范围需要明确。

最终候选的验证还要回到未被测试修改的原始候选字节。源图、场景、补丁、候选、规范 PNG、门禁和审阅记录建立完整哈希链；测试副本的结果不能替代最终文件身份验证。

### 14.10 忠实恢复与增强模式

`restore` 使用源图定义内容及布局约束，允许为不同字体渲染和图像采样设置经校准的容差，不主动改写文本、删减内容或套用新视觉系统。

`enhance` 必须先存在通过恢复门禁的忠实版本，再以它为内容与编辑性基线。合同另行声明允许调整的视觉属性与保护区域：

- 可以改善原生文字和图形的放大清晰度、非语义性轻微错位、间距、对比度和适配。
- 保留数字、结论、关系、图表比例与来源；颜色、大小和位置承载语义时加入保护约束。
- 超分辨率、补纹理或生成式修补不能为模糊文字、未知数值或遮挡内容提供事实依据。
- 增强版本接受完整内容、编辑性、页面和视觉审阅，并说明相对忠实版本的具体改善和偏离。
- 原图保真与增强目标分别计算，不通过放宽忠实恢复标准让增强版本自动过关。

审美选择通过具体页面审阅判断；可读性、对齐等测量是辅助证据。增强失败时保留已验收忠实版本，在报告中说明增强请求未完成；不能以失败增强版本替换它，也不能将整个请求标为完整成功。

### 14.11 结果状态、产物和拟议 CLI

恢复状态与报告执行完整性分别保存：

| `restorationStatus` | 含义                                                   | PPTX 发布策略                                  |
| ------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| `verified-native`   | 用户要求的语义对象全部通过原生构建、编辑及质量验收     | 可发布已验证候选，正常照片等仍可为原生图片对象 |
| `verified-hybrid`   | 用户明确允许的混合表示通过验收，指定编辑目标已全部完成 | 可发布，并逐区域说明原生与栅格内容             |
| `partial`           | 已完成部分恢复，但请求目标或必要验证尚未全部满足       | 默认交付报告与预览，候选保留在运行目录         |
| `needs-source`      | 缺少关键文字、数据、背景或其他必需信息                 | 报告列出最小补充项，不能发布为完成恢复         |
| `failed`            | 输入不可用、必要能力失败或无法形成有效候选             | 保留实际诊断及已有证据，不伪造恢复文件         |

混合表示不是自动降低要求的通道。用户要求完整编辑而有文字或数据区域仍为截图时，必须是 `partial` 或 `needs-source`。只有满足用户本来的局部目标或明确接受的范围，才能标记为已验证混合恢复。

报告的 `kind=image-restore` 在公共模型上扩展 `restoration`，包含合同/场景身份、状态、对象映射、表示选择、未恢复区域、验收结果和实际发布状态。发布状态另记为 `blocked / published / not-requested`，不通过报告生成成功推导 PPTX 可交付。

建议产物：

```text
.pptx-nova/<restore-run>/
├── xdoc-capabilities.json
├── source-manifest.json
├── normalized-reference/
├── recognition.json
├── restoration-contract.json
├── scene.json
├── candidates/
│   ├── 01/                   # patch、候选和真实渲染，逐轮保留
│   └── 02/
├── edit-tests/               # 实际编辑测试的独立副本与结果
├── visual-evidence/
├── restoration-gate.json
└── publication-manifest.json

restoration-output/
├── restored.pptx             # 仅通过对应发布门禁时出现
├── enhanced.pptx             # 请求增强且单独通过时出现
├── report.html
├── report.md                 # 按请求生成
├── report.json
├── manifest.json
└── assets/                   # 原图与候选对照、关键区域等交付资源
```

内部文件按实际执行生成，不创建虚假的成功占位物。原始输入仍在原位置只读；报告中引用的图像证据物化到交付目录。发布前验证输入未变化和候选字节与审阅一致，交付目录禁止覆盖已有用户内容。

拟议新增入口如下，所有参数均属于待实现的 skill 脚本，不是现有 `xdoc` 参数：

```bash
node <skill-root>/scripts/cli/restore/from-image.mjs \
  --input slide.png --mode restore \
  --editability all-content \
  --output-dir ./restoration-output --locale zh-CN

node <skill-root>/scripts/cli/restore/from-image.mjs \
  --input diagram.png --mode enhance \
  --contract ./restoration-contract.json \
  --output-dir ./diagram-restoration --locale zh-CN
```

`all-content` 表示所有可见语义内容都在恢复目标中，并按对象角色选择正确原生表示；照片不要求被拆成绘图元素。局部目标由合同明确列出，不设置能够默默排除困难内容的“自动完成率”参数。Agent 可以从用户直接请求准备合同，无需用户手写 JSON。

退出码沿用第 8.4 节的参数和输出错误分类，但恢复入口对 `0` 的含义更严格：请求的 PPTX 产物已经通过门禁并发布；`3` 表示可读报告已交付而恢复/增强请求未完整完成；`4` 表示有效分析或候选构建失败。底层退出码原样保存，不能仅因报告已生成返回恢复成功。

### 14.12 新增模块与运行时职责

建议的 skill 内部布局：

```text
scripts/cli/restore/
    from-image.mjs
scripts/lib/restoration/
    contract.mjs
    recognition.mjs
    scene.mjs
    compile.mjs
    fit.mjs
    verify.mjs
    publish.mjs
```

模块按实际职责保持适度规模，复用报告层和已有证据模块；内部库不 import CLI。场景及恢复合同的 Schema 与验证器自包含在 skill 内。

能力分工：

| 层次               | 职责                                               | 实施要求                                                         |
| ------------------ | -------------------------------------------------- | ---------------------------------------------------------------- |
| Agent/识别适配     | 语义理解、识别候选、关系推断、真实看图复核         | 保存输入、结果和可取得的提供方信息；不能以自报置信度作为通过证据 |
| 确定性图像与测量层 | 解码、尺寸、裁剪、坐标变换、字形测量、局部图像比较 | 优先由本地 xdoc 运行时提供可发现、可测试的有界能力               |
| 场景编译与校准     | 合同验证、类型化操作、约束拟合及候选管理           | `.mjs`，使用 Node 内置模块及已发布 xdoc                          |
| xdoc 原生构建      | 支持子集的对象写入、dry-run、回读、渲染与原生检查  | 以当次真实 Schema 和各能力轴为准                                 |
| 恢复验收与发布     | 内容、编辑性、图像保真、报告与最终身份验证         | 新增恢复消费者，保留并满足适用的现有关卡                         |

识别适配层可使用执行环境已提供的多模态能力作为初始候选来源。需要精细 OCR/分割时，应提供明确可配置的适配契约；不能为了运行而要求用户临时安装 Python OCR、浏览器或第三方 npm 依赖，也不能自动把材料上传到新的外部服务。

当现有运行时没有图像处理、真实字体测量或区域比较契约时，将其列为明确的运行时增强前置项，先实现并验证后再开放对应质量承诺。不得在方案或帮助文档中把拟议能力写成已经存在的命令，亦不通过脚本封装掩盖缺失能力。

规范候选视觉检查用于证明实际创建质量；新增原图保真验收用于证明图片恢复目标。二者结果并列消费，不改写原生 `decision`，不把图片参考文件当作原始语义 PPTX，也不复用错误的工作流消费者绕过发布约束。

### 14.13 实施阶段与完成条件

| 阶段              | 具体交付                                                                                     | 完成条件                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| E：输入与合同     | 输入质量评估、源身份与规范化变换、恢复合同、场景 Schema、识别适配接口                        | 来源与字段确定性可追溯；歧义与缺失能阻断成功，不会被默认补全                   |
| F：忠实恢复闭环   | 清晰文字、基础形状、连接线、分组和原始图像资源；确定性编译、字体拟合、局部比较与最佳候选回退 | 在声明场景中通过内容、编辑、视觉和文件门禁；无背景旧字、无伪编辑覆盖层         |
| G：结构与数据对象 | 原生表格、可靠数据图表、公式受支持子集；逐类型编辑测试和复杂局部失败处理                     | 数据与关系有据可核；目标未完成不能计入成功；图表与公式实际目标环境验证满足合同 |
| H：增强与交付     | 独立增强合同、基线保护、恢复报告、资源完整性、最终发布及文档                                 | 忠实版和增强版独立验收；最终产物与审阅字节一致；实际案例证明可编辑与视觉质量   |

依赖顺序为 E → F → G/H；H 中的增强以相应对象的恢复门禁通过为前置。Compare/Check 报告层可复用，但图片恢复不依赖其尚不存在的跨页语义匹配能力。

第一批对外支持范围由通过验证的内容族确定，例如清晰文本页、卡片页、二维流程图、表格和数据完整的常见二维图表。扩大范围前补齐对应内容族的正例、负例、能力边界和回归证据。范围收敛的依据是质量可验证性，不用自动降级来维持表面成功率。

### 14.14 恢复专项验证矩阵

| 场景                                 | 必须验证的结果                                         |
| ------------------------------------ | ------------------------------------------------------ |
| 中英混排、富文本、长段落、细小脚注   | 文本与阅读顺序正确，实际字体可用，强调及文字布局可核实 |
| 小数点、负号、百分号、单位、相似字符 | 关键差异不会被全页视觉指标掩盖，不能用上下文猜值       |
| 透明背景、渐变、图片上的文字         | 无重影、遮盖或假背景；无法分离时正确给出未恢复状态     |
| 节点交叉、箭头方向、重复对象         | 关系正确，对象身份稳定，编辑测试能够发现错误连接       |
| 合并表格、空白和不可见数据           | 网格、合并及可见内容正确；未知数据不被补写             |
| 有精确数据和无精确数据的图表         | 分别形成可核实原生图表或明确未完成状态，不伪造数据     |
| 公式、特殊符号及不支持的对象         | 原生编辑声明与实际表示一致，关键内容不丢失             |
| 模糊、压缩、透视、遮挡、裁切         | 规范化变换可追溯，信息不足进入待核实而非自动补全       |
| 两个候选分别在不同区域较好           | 优化接受策略保留硬约束，局部改善不覆盖其他区域退化     |
| 字体缺失、运行时升级、缓存命中       | 不使用不适用的旧验收结果，环境变化触发相关复核         |
| 全内容恢复和局部目标恢复             | 覆盖分母来自合同，困难目标不被自动排除                 |
| 忠实版通过、增强版失败               | 保留忠实版与失败证据，正确报告请求未全部完成           |
| 原图、场景、补丁或候选被替换         | 哈希链识别证据失效，拒绝成功发布                       |

测试样本应同时包括已知文本/数据/结构的原生源截图，以及没有原始对象的真实输入。前者可量化识别和重建误差，后者用于检验局限、人工复核与实际使用体验；两者不能混作同一真实性证明。

建立正常样本、单字符/单数值/单连接错误等负例，以及独立于拟合调参的验证集。记录关键内容正确性、强制对象完成情况、局部视觉失败、人工确认项、迭代次数、耗时与产物大小，不仅报告整体相似度和成功率。

实际 PowerPoint 编辑、重开及渲染验证按可用环境组织条件覆盖；当合同要求该证据时，缺失必须阻断相应承诺。仅在 xdoc 中通过渲染不能宣称 Office 像素完全一致。

- [ ] 原图只读，规范化、识别、场景和构建结果有完整来源与身份绑定。
