# DeckKit 视觉验收：复用检查与真实反例

创建、迁移或修改会影响画面的 DeckKit 时，在首次 PNG 走查前阅读本文件。适用于 PPTX、HTML、
设计文档与参考图输入。这些要求约束生成器质量，不固定任何主题的版式。

## 逐页验收

原生宿主检查图表标签时，核对整数尾随小数点、常规小数、科学记数、负数与零；canonical PNG
可能使用等值但不同的显示格式。分别记录显示与原始数值，不能用 PNG 正常推断 PowerPoint 格式正常。
Warm Clay 的 `0.##` 曾在 canonical 显示 `48`，在 PowerPoint 显示 `48.`。应按实际数值选择
整数、小数或科学记数格式，再分别验证；不要修改原始数值来消除显示缺陷。

逐页查看同一候选 PPTX 的 canonical PNG，不能只看 contact sheet、抽查代表页或读机器报告。
golden、构图变体、压力与多语言验证中准备接受的每一页都要检查。机器零 findings 仍可能有明显
的居中、边距和分组问题；打开图片不等于已经认真检查全部细节。

每页检查实际画面：

1. 标题、标签、正文是否完整，有无伸出底色、压线、截断或不合理孤行。
2. 圆形编号、badge、阶段块的文字是否在容器内正确对齐，四周留白是否合理。
3. 表头、单元格、图例、来源和页码是否可读，相邻数值是否挤在一起。
4. 图表标签是否对应数据对象，内部标签与每段底色是否有足够对比度，连接线是否贴合目标。
5. 表格主体、底边、附注、阶段门槛和结论条之间是否有可辨认的间距与分组。
6. 中英文实际字体、粗体/斜体、标点和数字是否符合预期，有无意外字体替代。
7. 横向/纵向构图中的分隔线是否止于组件内部；流程及反馈的箭头是否与路径端点相连。
   零高度/零宽度路径的箭头须用可见 viewport 核对，不能用操作成功代替实际箭头检查。
   开放式表格、指标带和编号列表的结论须与最后一条规则线留出可辨认的间距。
   流程轴也须避开步骤标题的实际字形基线；列分隔线应在底部机制/附注规则线之前结束。
   Warm Clay 曾在机器零 findings 时仍出现这两类贴线问题，必须看同一候选的局部图。
8. 已盘点的风格细节是否逐项保留：圆点、粗短线、刻线、引线、行内注记和时间刻度的实际
   长度、位置、字重及留白是否仍有原稿的辨识度；检查贴底/出血图形和底栏交界有无白缝。
   功能相同、组件存在或大致配色相似，不能单独证明这些细节已迁移。

编号节点、带底色标签、密集矩阵、图表内部数值和底边附注需要局部放大检查。放大图从同一
canonical PNG 裁出，不另渲染不同 PPTX。逐个看清，不以“同类应该一样”略过。

## 三类真实反例

Green Slate 首轮在机器检查通过后，由用户发现以下缺陷。原先 Agent 的视觉验收因此不成立。

| 漏检                             | 根因                                                        | 修复与复验原则                                                                                                      |
| -------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 圆内数字偏左上                   | 独立文本框近似摆在圆内，没有双向居中                        | 优先把文字写入原生圆形：统一内边距、`verticalAnchor: middle`、段落 `alignment: center`；放大检查每个编号及横/纵变体 |
| `EXECUTIVE SUMMARY` 超出绿色底条 | 背景按字符数估宽，文字框却是独立固定宽度                    | 背景与文字共用容器或几何事实源；明确内边距，估宽覆盖粗体大写、MW 宽字及 CJK；最终检查真实 PNG                       |
| G1/G2/G3 说明贴着表格底线        | 轨道、横线和说明分别使用 magic offset，没有共同预留底部空间 | 先分配说明区及间距，再从总高度推导主体行高；纵线停在主体区域，不穿过说明                                            |

不要用缩小字体、隐藏文字、删除合法字段、改变门禁阈值或豁免处理这些问题。
宽度估计不是字体真实测量；设置了 center 也不等于视觉居中已成立。

### 形状内文字

- 圆形编号优先由圆形自身持有文字，避免两套几何漂移。标签条和阶段块同理。
- 必须分离时，背景与文字共用 frame/inset 计算，并检查字形没有越界。
- 字形墨迹中心与 advance 中心可能略有差异，光学修正须有图片证据。
- 组件测试覆盖短文字、最长合理文字、粗体大写、CJK/Latin，以及实际支持的两位编号。

### 分隔线与说明区

- 先分配表头、主体、说明、结论、页脚区域，再推导行高和线段终点。
- 附注不是最后一行单元格：底边与说明字形之间应有可见留白。间距依据字号、密度和阅读分组
  决定，不能只比较 textbox bbox 是否不重叠。
- 用最大合理行数、阶段数及较长门槛复验；三阶段修好后还要检查支持的四阶段边界。
- 间距写入合同或明确的共享布局参数，避免逐页凑坐标。

### 字体与数据标签

- 整页预览疑似缺字或数字消失时，先从同一原 PNG 裁切放大，核对实际像素再归因。
  PDF 文本提取、字体查询与原生宿主可交叉定位，但任何一项都不能单独证明 PNG 已绘制。
  Amber Ledger 曾把整页缩览误读为字体/并发缺字；同 PNG 放大证实字形存在，已撤回归因。
  保留原始证据与更正，避免用更换字体掩盖尚未成立的问题。
- 图表属性须按 chart family 使用：本次 runtime 对非折线的 `smooth`、非柱/条的
  `invertIfNegative` 曾在 schema 接受后报告非法 XML child。检查 apply 的 warning 和语义报告，
  修生成端并复验；schema 接受和进程退出成功不等于原生包有效。此观察不替代当前 focused schema。
- 极小值须查看刻度和数据几何，不能只检查数字 cache。若使用数值派生原生形状，保留同源数值，
  披露原生 chart 与可编辑 shape 的边界，并验证零、负数和保存重开。数据编码的柱高或累计位置
  被误判为卡片不齐时，保留原告警及人工判读；不能为消噪把数据图形强行对齐。
- 字体名存在不代表匹配正确。用 `fc-match` 或平台等效工具检查实际文件/style，再对照 PNG。
  Green Slate 曾发现 Sarasa 匹配成 Italic；另一字体虽然系统查询显示正体，实际 CJK 粗体仍倾斜。
  因此至少用实际支持的 Latin/CJK、常规/粗体做原生文本渲染探针，不能仅凭字体查询放行。
- 堆叠条内部标签逐段检查对比度；属于允许调色板不代表可读。
- 对照最终 PNG 检查标签是否真的出现。Clear Value 曾发现逐系列 font 覆盖导致内部值消失；
  机器零 findings 没有发现该问题。当前采用浅色/描边与统一深色标签，不能把这个 workaround
  当作所有 runtime 的永久限制。环图须同时看类别、数值与小扇区标签，面积圆须核对面积比例。
- 原生图表数据编辑探针须同时回读嵌入工作表、图表 cache 并重新原生渲染。Warm Clay 在一台
  macOS Office 主机上出现工作表已修改而 cache/画面仍旧的情况；不能把“能打开 Excel”或
  “输入已保存”记成图表数值同步通过。记录实际宿主和同步边界，生成端仍保持两者同源。
- 原生 PDF 导出和编辑器/放映显示也须分开记录；发生差异时保留异常产物，改用身份绑定的
  放映窗口检查实际显示，不能把有缺字/位移的 PDF 记成通过。窗口必须完全位于当前屏幕内；
  若默认宽度越出屏幕导致 canvas-scale 门禁失败，缩小窗口后重采集，不放宽身份门禁。
- 图表的 series 名称等原生元数据不一定可见。业务字符串的可见槽位探针必须有真实文字所有者；
  隐藏图例时，按表达需要将系列名与单位显式排在图旁，不能用 chart cache 中存在字符串代替检查。
- 条形图同时覆盖负数、零和极小值。负数 outside-end 标签可能贴近类别名称，即使机器没有告警；
  检查轴域留白与标签间距，保留原始值，不能靠伪造最小条长解决。表格最后一行和来源也须放大复核。
- 明确记录字体替代与跨平台限制，不下载或打包来源不明的字体。

## 逐页记录与返修

在当前 run 的 `visual-review-ledger.md` 或 JSON 记录候选 PPTX hash、manifest、冻结日期，
以及每页 PNG/hash、检查结果、问题、修复轮次与复验结果。未查看/有问题的页保持 pending/fix，
不要脚本预填全部 pass。先列检查项，再逐张看图填写结果。

修复后生成新候选和新证据；最终完整样例重做逐页走查，受影响的变体和边界输入重跑。
不能将旧候选 review 改个路径沿用。用户指出漏检后撤回受影响结论，记录遗漏的检查类别，
主动排查全部同类组件，而不只修用户指出的实例。

验收记录至少回答：哪一版文件、哪些页面已看、发现了什么、改在哪里、哪一轮复验通过。
截图已打开、脚本成功、文档补了规则，均不能作为“全部视觉通过”的依据。最终报告明确区分
机器检查通过与人工逐页通过；仍有 pending/fix 时不得宣布 DeckKit 已完成验收。

## 可选的实际像素诊断

源码仓库维护者工具（Node 内置模块 + 可选 ImageMagick）：

```bash
node tools/pptx-nova-enclosed-text-audit.mjs \
  --patch <run>/patch.json --previews <run>/canonical/candidate \
  --out <run>/enclosed-text-audit.json
```

当前仅适用于 13⅓×7.5in 画布、小型原生圆/矩形、显式实体字色与 `slide-N.png` 预览。
检查字色掩码边界、圆内中心偏移及独立覆盖的文本框。6% 是诊断容差，不是通用光学标准。
透明/渐变、邻近同色对象、复杂字形、裁切和缺字可能使结果不适用；不得扩大 coverage。
缺少 ImageMagick 返回 unavailable，不算通过。

Green Slate 的旧版反例能被该工具检出；修复版仍须实际看图。不得加入 pptx-nova 必需用户路径，
也不得替代逐页审查。
